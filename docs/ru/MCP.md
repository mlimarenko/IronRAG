## Адрес сервера

- Адрес: `http://127.0.0.1:19000/v1/mcp`
- Транспорт: **MCP Streamable HTTP, spec `2025-11-25`**. Один адрес принимает `POST`, `GET` и `DELETE`; отдельного SSE-канала и stdio-прокси нет.
  - `POST` - все сообщения JSON-RPC. Формат ответа выбирается заголовком `Accept`:
    - `Accept: application/json` - ответ приходит обычным JSON (по умолчанию, удобно для curl).
    - `Accept: application/json, text/event-stream` - ответ приходит одним SSE-фреймом `event: message\ndata: …\n\n`; SDK-клиент, объявивший оба формата, получает ожидаемый транспорт.
    - Запросы без `id` (уведомления) подтверждаются ответом `202 Accepted` без тела.
  - `GET` зарезервирован для потока событий сервера. IronRAG пока не отправляет фоновых уведомлений, поэтому отвечает `200 OK` с `Content-Type: text/event-stream` и единственным SSE-комментарием `: ready`, после чего молчит. Спецификация `2025-11-25` допускает и `405`, и пустой поток; выбран второй вариант, потому что некоторые поставляемые MCP-клиенты считают любой ответ, кроме `200`, на этапе установки соединения фатальным и отключают сервер в контексте агента.
  - `DELETE` закрывает сессию, принадлежащую клиенту. Сервер записывает распределённый tombstone с ограниченным TTL, отклоняет последующие вызовы этой сессии и прерывает её текущую работу на любой реплике API. Повторное закрытие того же владельца идемпотентно, пока tombstone активен.
- `initialize` возвращает заголовок `Mcp-Session-Id` (UUIDv7). Каждый последующий `POST`, `GET` и `DELETE` обязан повторить ровно это значение и отправить `Mcp-Protocol-Version: 2025-11-25`. Отсутствующая, некорректная, истёкшая, завершённая или чужая сессия отклоняется; неподдерживаемый либо дублированный заголовок версии также не принимается. На корректный `initialize` с другой версией сервер возвращает в результате единственную поддерживаемую версию; клиент без её поддержки должен отключиться.
- Клиент вне браузера может не отправлять `Origin`. Если заголовок есть, он должен содержать ровно один origin в нормализованной ASCII-форме, точно совпадающий с `IRONRAG_FRONTEND_ORIGIN` или необязательным `IRONRAG_OPENAPI_PUBLIC_ORIGIN`. Дублированное, некорректное, иначе сериализованное или недоверенное значение получает `403` до авторизации, чтения сессии и разбора JSON.
- Capabilities (для мониторинга и UI): `GET http://127.0.0.1:19000/v1/mcp/capabilities`. Это не часть протокола MCP, а отдельная проверка состояния.
- Авторизация: `Authorization: Bearer <token>` на каждом запросе (включая `GET`/`DELETE`).
- Имя MCP-сервера на протокольном уровне: `ironrag-mcp-memory`.
- Имя клиента в готовых сниппетах админки: `ironragMemory`.

Быстрая проверка (JSON):

```bash
export IRONRAG_MCP_TOKEN='inrg_...'

curl -sS -X POST http://127.0.0.1:19000/v1/mcp \
  -H "Authorization: Bearer $IRONRAG_MCP_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-11-25","capabilities":{},"clientInfo":{"name":"manual-probe","version":"1"}}}'
```

Быстрая проверка (SSE-фрейм, как у SDK-клиентов):

```bash
curl -sS -X POST http://127.0.0.1:19000/v1/mcp \
  -H "Authorization: Bearer $IRONRAG_MCP_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":2,"method":"initialize","params":{"protocolVersion":"2025-11-25","capabilities":{},"clientInfo":{"name":"manual-probe","version":"1"}}}'
```

Если IronRAG стоит за прокси или под другим доменом, подставьте тот origin, который реально видит клиент.

## Подключение за минуту

1. Поднимите IronRAG через Docker Compose.
2. В `Admin -> Access` создайте API-токен и сохраните его: открытое значение показывается только при создании.
3. Выдайте разрешения на рабочее пространство, библиотеку или документ, которые агент должен видеть.
4. В `Admin -> MCP` скопируйте готовый фрагмент конфигурации для клиента.

`tools/list` фильтруется выданными правами: недоступный токену инструмент не показывается.
Набор методов JSON-RPC: `initialize`, `tools/list`, `tools/call`, `resources/list`, `resources/read`, `resources/templates/list` и `notifications/initialized`. `initialize` объявляет возможности `tools` и `resources`; подписка на изменения ресурсов не поддерживается.
Аргументы инструментов принимаются только в camelCase.
Цели каталога задаются стабильными ref вместо непрозрачных UUID: `workspace` имеет вид `<workspace>`, `library` - `<workspace>/<library>`. Ответы списков возвращают эти значения в поле `ref`.

## Инструменты

Текст результата инструмента самодостаточен: `content[].text` содержит результат целиком (JSON), а `structuredContent` повторяет его в машиночитаемом виде для клиентов, которые читают его напрямую. Клиенты, передающие модели только текст (opencode, Claude Code, Codex), получают данные без обращения к `structuredContent`.

### Grounded Q&A (основной инструмент для вопросов по базе знаний)

| Инструмент | Описание | Обязательные параметры |
|------------|----------|----------------------|
| `grounded_answer` | Задать вопрос обычным языком и получить ответ по материалам библиотеки со ссылками на источники. Выбирайте его вместо `search_documents` + `read_document`, когда нужен ответ, а не список найденного. | `library`, `query` |

Форма ответа: текст результата содержит ответ. Профиль `compact` по умолчанию отдаёт ограниченные ссылки и предупреждения, типизированное состояние проверки, готовности и полноты, repair policy и идентификаторы трассировки, не дублируя диагностический объект исполнения. Запрашивайте `responseProfile: "full"` только когда операционному клиенту нужен `executionDetail` с полями chunk, prepared-segment, technical-fact, graph-entity, graph-relation, runtime, request и response. Верхнеуровневые `runtimeExecutionId`, `executionId` и `conversationId` в обоих профилях остаются короткими ссылками для поиска трассировки. Встроенный ассистент UI использует те же инструменты MCP: он может вызвать `grounded_answer`, посмотреть сырые инструменты поиска и чтения или ответить напрямую, когда поиск по библиотеке не нужен. Внешние MCP-клиенты получают тот же набор инструментов, те же схемы и тот же контракт результата `grounded_answer`.

Если семантический отчёт сохранён, профиль `full` возвращает его в
`executionDetail.semanticVerification`. Отчёт привязан к точному вопросу,
проверенному кандидату и допущенному набору источников. `visibleAnswerSha256`
обозначает итоговый видимый текст: если он отличается от `checkedAnswerSha256`,
выводы относятся к кандидату, а не к заменившему его ответу. Завершённая
проверка, подтверждение утверждений, полнота и классификация отказа не означают
готовности ответа. Неуспешная или незапущенная проверка не подтверждает ответ, а
корректный отказ отвечать из-за нехватки источников не подтверждает
запрошенный факт. Исполнениям без отчёта не приписывается выдуманный результат.

Компактный `semanticVerification` явно помечен `projection: "summary"`. В нём
сохраняются точные хеши текстов и общие исходы, возвращается не более восьми
находок по утверждениям и оговоркам и запрошенное ограниченное число
источников; общие счётчики и признак усечения указаны отдельно. Исходный текст и
цитаты не включены, а сокращённый текст находок помечается. Это не канонический
отчёт, и по нему нельзя повторно использовать вывод проверки. Точный проверенный
текст и проверенные цитаты доступны в полных данных исполнения при наличии
разрешения.

| Инструмент | Описание | Обязательные параметры |
|------------|----------|----------------------|
| `search_documents` | Поиск по памяти библиотеки с результатами на уровне документов. Поиск можно сузить списком ref через `libraries`. | `query` |
| `read_document` | Прочитать документ полностью или фрагментом. | `documentId` |

опубликованной ревизии. `sliceStartOffset`, `sliceEndOffset` и
`totalContentLength` считают символы Unicode в том же тексте, включая пробелы и
переносы строк. Описание изображения остаётся в отдельном поле
`visualDescription` и не меняет координаты документа. `mode: "full"` означает
полное чтение, только если окно начинается с нуля, заканчивается на полной
длине и продолжения нет.

### Диагностика загрузки

Только диагностический mount. Для чтения истории загрузок библиотеки нужно одно из прав: `library_read`, `document_read`, `document_write`, `connector_admin`, `ops_read`, `workspace_admin` (роль) на эту библиотеку. Повтор и отмена требуют одного из `connector_admin`, `library_write`, `workspace_admin`, поэтому токен только для чтения видит два читающих инструмента и не видит изменяющих.

| Инструмент | Описание | Обязательные параметры |
|------------|----------|----------------------|
| `list_ingest_jobs` | Список заданий загрузки библиотеки, новые первыми, с фильтром по состоянию очереди и постраничной выдачей. | `library` |
| `get_ingest_job` | Загрузить одно задание с последними попытками и таймлайном стадий последней возвращённой попытки. | `jobId` |
| `retry_ingest_job` | Вернуть в очередь задание в состоянии queued, paused или с истёкшей арендой; completed, canceled и failed отклоняются. | `jobId` |

Эти инструменты требуют вызывающего, который определяется как системный администратор; широких прав на библиотеки недостаточно.

| Инструмент | Описание | Обязательные параметры |

| `mint_iam_token` | Выпустить API-токен с указанными правами; открытое значение возвращается один раз. | `label` |
| `update_iam_token` | Изменить метку или срок действия API-токена; `expiresAt: null` снимает срок, область прав после выпуска неизменна. | `tokenId` |
| `revoke_iam_token` | Отозвать API-токен по идентификатору его principal. | `tokenId` |

Внутри MCP использует те же сервисы, что и веб-приложение: PostgreSQL для служебного состояния и данных базы знаний, а также фоновые обработчики загрузки документов на Redis.

## Ресурсы

Сервер объявляет возможность `resources` и отдаёт два ресурса:

| URI | MIME-тип | Содержимое |
|-----|----------|------------|
| `ironrag://manifest` | `application/json` | Манифест сервера: имя и версия, версии JSON-RPC и протокола, заголовки сессии, поверхность (`answer` или `diagnostics`), версия и хеш контракта инструментов, видимые инструменты и список ресурсов. |
| `ironrag://typescript` | `text/typescript` | TypeScript-объявления, сгенерированные из того же контракта: `IronRagToolName`, `IronRagManifest` и интерфейс входных аргументов для каждого видимого инструмента. |

Оба ресурса строятся из того же контракта, что и `tools/list`, поэтому токен видит только доступные ему инструменты, а вывод детерминирован при неизменных правах и схемах. В манифесте нет времени генерации и случайных идентификаторов. Методы: `resources/list` возвращает список ресурсов, `resources/read` с `{ "uri": "..." }` — содержимое, `resources/templates/list` — пустой список, потому что шаблонов нет.

## Контракт качества инструментов графа

- `get_graph_topology` не отдаёт полный дамп графа. Когда срабатывает `limit`, IronRAG сначала оставляет наиболее подтверждённые сущности, затем только связи, у которых обе вершины остались видимыми, и только потом привязки документов и документы, которые действительно поддерживают этот видимый срез.
- `search_entities` работает с тем же снимком текущего графа, что и `get_graph_topology`. Если сущность видна в текущем графе, `search_entities` должен находить её по тому же словарю, а не опираться на параллельный устаревший индекс.
- `list_relations` ранжируется по `support_count`, то есть по числу подтверждений, а не по порядку вставки в таблицу.
- Инструменты графа должны давать агенту связный полезный подграф, а не алфавитный или случайный фрагмент с висячими рёбрами и нерелевантными документами.
- При проверке клиента оценивайте не только форму JSON, но и полезность результата: сильные сущности должны стабильно идти первыми, связи - по числу подтверждений, ссылки на документы - только на те узлы и рёбра, которые остались в ответе, а `list_relations` не должен вырождаться в метки `unknown`.
- Повторяющиеся после нормализации подписи сущностей и повторы одной и той же связи `(source, relationType, target)` внутри одного среза выдачи - регрессия качества, а не безобидный косметический шум.

## Модель доступа

- Токены можно ограничивать конкретными рабочими пространствами и библиотеками.
- Токены только для чтения подходят для ассистентов, которым нужен только поиск, чтение и ответы на вопросы.
- Токены с правом записи могут загружать, обновлять и удалять документы, если агент сам поддерживает базу знаний.
- Видимость инструментов определяется выданными правами: клиент видит только разрешённое.
- Если токен ограничен ровно одним рабочим пространством или библиотекой, инструменты MCP могут вывести ref `workspace` или `library` из области токена, и агенту не нужно передавать его каждый раз явно.

## Что получает клиент

- Те же документы и поиск с источниками, что использует встроенный ассистент.
- То же состояние документов, что используется при загрузке, обновлении, поиске и просмотре графа.
- Подключение внутреннего бота или персонального агента к управляемой базе знаний без отдельного адаптера.

## Claude Code (remote MCP)

```bash
claude mcp add ironrag http://127.0.0.1:19000/v1/mcp \
  --transport http \
  --header "Authorization: Bearer $IRONRAG_MCP_TOKEN"
```

`claude` подключается напрямую через Streamable HTTP — отдельный stdio-прокси не нужен.
