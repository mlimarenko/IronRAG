# Биллинг и отчётность по стоимости

Как вызов провайдера превращается в отражённую стоимость и что означает
показанное число.

## 1. Четыре стадии

| Стадия | Таблица | Когда пишется |
|---|---|---|
| Резервация | `billing_provider_call` | до платного запроса (состояние `started`) |
| Использование | `billing_usage` | после ответа провайдера, по строке на billing unit (input / output / cached input) |
| Начисление | `billing_charge` | после записи usage; читает подходящую ставку из строки модели и пишется всегда |
| Rollup | `billing_execution_cost` | пересчёт по execution после изменения usage |

Резервация создаётся до запроса, чтобы неоднозначный таймаут всегда можно
было согласовать. Usage коммитится до терминального исхода запроса.
Для новых вызовов валидация модели гарантирует наличие цен, необходимых для
записи начислений.

## 2. Цена хранится в модели

Цена входит в каждую строку `ai_model_catalog`: `currencyCode` и ставки за
миллион токенов input, cached input, cache-write input и output. Модель также
может задавать long-context tier с `thresholdTokens` и ставками input,
cached-input и output. Запросы создания и обновления модели требуют цены,
поэтому для новых вызовов отсутствие подходящей ставки структурно невозможно.

Каждая seeded-модель содержит реальные тарифы вендора. При старте строки
seeded-моделей обновляются из seed, поэтому изменения их цен оператором
перезаписываются после рестарта. Модели, созданные оператором, сохраняют
настроенные значения.

**Цены применяются в момент фиксации.** `billing_charge` копирует
`unit_price` из цены модели, действующей при фиксации usage, и не ссылается
на отдельную строку цены. Изменение цены модели никогда не переписывает
историю начислений. Историческая переоценка потребовала бы явного backfill
с пометкой соответствующих rollup'ов грязными; такого механизма сейчас нет.

## 3. Что означает показанная стоимость

Каждое чтение стоимости (`BillingExecutionCost`, `DocumentCostSummary`,
`LibraryCostSummary`, `WorkspaceCostSummary`) несёт три числа, которые
читаются только вместе:

- `totalCost` — сумма реально записанных начислений.
- `providerCallCount` — все вызовы в скоупе из `billing_provider_call`,
  с ценой или без.
- `unpricedProviderCallCount` — исторические вызовы, у которых хотя бы один
  юнит usage остался без цены. Частично оценённый вызов считается один раз, поэтому
  число сопоставимо с `providerCallCount`.

`costCoverage` (`CostCoverageStatus`) выводится из двух последних; именно по
нему должен ветвиться клиент. Новые вызовы всегда имеют `complete`; сохранённые
вызовы с недостающими ценами используют `partial` или `unknown`:

| Coverage | Смысл | Что обязан показать UI |
|---|---|---|
| `complete` | все вызовы с ценой (или вызовов нет) | сумму |
| `partial` | часть с ценой, часть без | сумму как нижнюю границу + счётчик без цены |
| `unknown` | вызовы есть, ни одного с ценой | «стоимость неизвестна», никогда `$0.00` |

Нулевая сумма сама по себе неоднозначна и не должна рендериться как
«бесплатно».

## 4. Правила согласованности rollup

- Счётчик без цены считается в той же транзакции и под тем же advisory
  lock, что и агрегат начислений, и пишется вместе с остальным rollup —
  читатель не смешает счётчики двух поколений.
- Списки документов и фасеты читают здоровье rollup, строки и счётчики в
  одном read-only repeatable-read снимке, включая пустую выдачу. Обязательное
  поле `scopePending` описывает доступность запроса отдельно от
  `costRollupFreshness`. Metadata-выдача остаётся доступной, но стоимости
  скрываются. Сортировка по стоимости, действующий cost-фильтр и глобальный
  текстовый поиск требуют актуальных стоимостей: при reconciling они
  возвращают pending scope без строк, точных счётчиков и продолжения.
  Фасет исключает фильтр собственной колонки перед определением зависимости
  от стоимости; cost-фасет всегда зависит от актуальных стоимостей. Клиент
  начинает pending cost cursor chain с первой страницы, сохраняя pinned clock.
- Чтения cost-summary и document-costs не отдают 503 на грязном
  поколении. Они возвращают явный, независимый от coverage признак
  `costRollupFreshness`: `current` — все зафиксированные provider-вызовы
  свёрнуты в rollup; `reconciling` — хотя бы одно owning execution отстаёт.
  При `reconciling` summary скрывает все value-поля (`null`, никогда не
  фиктивный ноль и не устаревшая сумма), а страница document-costs отдаёт
  пустой список без курсора и без счётчика. Workspace-агрегат становится
  `reconciling`, если грязная любая из его библиотек; чистая библиотека
  остаётся `current`. Терминальный mixed-currency rollup по-прежнему 409.
- Usage без цены — не конфликт валют. Mixed-currency guard остаётся про
  расхождение валют реальных начислений; скоуп без начислений отдаёт
  placeholder `USD`, а рендерингом управляет coverage.
- Execution без строки rollup вообще не зафиксировал оплачиваемых вызовов —
  его ноль это `complete`. У execution с вызовами без цены строка rollup
  есть, и она сообщает число вызовов без цены.

## 5. Сохранённые вызовы без цены

При миграциях и обслуживании сохраняйте coverage и обработку в rollup
сохранённых вызовов без цены. Частично оценённый usage показывайте как нижнюю
границу стоимости, полностью неоценённый — как неизвестную стоимость, а не
как бесплатный usage. В новых
путях начисления отсутствие ставки модели должно считаться нарушением
инварианта, а не причиной пропустить charge.
