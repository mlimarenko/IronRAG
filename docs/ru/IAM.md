# IronRAG IAM

[Обзор](./README.md) | [MCP](./MCP.md) | [CLI](./CLI.md)

IronRAG использует одну модель авторизации для веб-интерфейса, HTTP API,
токенов, созданных через CLI, и инструментов MCP.

## Базовые понятия

| Термин | Смысл |
|---|---|
| Principal | аутентифицированная сущность: пользователь или API-токен |
| Grant | разрешение, назначенное в определённой области |
| Scope | область: `system`, `workspace`, `library` или `document` |
| Permission kind | именованная возможность, например `library_read` или `iam_admin` |
| Token | секрет bearer-аутентификации с префиксом `inrg_` |

## Виды разрешений

| Permission | Назначение |
|---|---|
| `iam_admin` | полное системное администрирование |
| `workspace_admin` | управление рабочими пространствами и библиотеками |
| `workspace_read` | чтение метаданных рабочего пространства |
| `library_read` | чтение библиотек, документов, графа и связанных данных |
| `library_write` | загрузка, изменение, удаление и веб-приём содержимого |
| `document_read` | чтение конкретного документа |
| `document_write` | мутация конкретного документа |
| `query_run` | запуск хода поиска и ответа |
| `ops_read` | чтение состояния выполнения и эксплуатации |
| `audit_read` | чтение событий аудита |
| `credential_admin` | управление учётными данными провайдеров |
| `binding_admin` | управление привязками моделей и предустановками |
| `connector_admin` | управление коннекторами |

## Иерархия разрешений

- `iam_admin` подразумевает `workspace_admin`, который подразумевает все остальные разрешения.
- `library_write` подразумевает `library_read` и разрешения на чтение и запись документа.

## Полномочие интеграционного провижининга

Интеграционный провижинер — корневая worker identity, которую утверждённый
OIDC-администратор создаёт с `provisioningAuthority=integration`. Обычный grant
на workspace — только `workspace_read` для чтения каталога. Создание ресурсов,
управление дочерними ключами и удаление идут через `/v1/provisioning/*`, где
авторизация привязана к неизменяемому `provisioned_by_principal_id`. Сторонний
grant не подтверждает владение.

Существующие ресурсы интеграции один раз назначаются командой
`ironrag-maintenance migrate integration-provisioning-ownership` с явными UUID
authority, workspace и каждой library. Команда не принимает имена, отклоняет
неактивные ресурсы, library другого workspace и строки с уже назначенным
владельцем. Обычные API routes не могут назначить или сменить владельца.

## Иерархия scope

Более широкая область покрывает более узкий ресурс:

```text
system
  -> workspace
    -> library
      -> document
```

Область **system** (`workspace_id=null`) даёт полный административный доступ ко
всем рабочим пространствам. Токен этой области не привязан к одному рабочему
пространству.

Примеры:

- `library_read` в рабочем пространстве покрывает все его библиотеки.
- `document_write` на одном документе не дает доступа к соседним документам.
- `iam_admin` на `system` обходит per-resource checks.

## Маршруты сессии и токенов

Маршруты сессии:

- `POST /v1/iam/sessions`
- `GET /v1/iam/context`
- `POST /v1/iam/session`
- `GET /v1/iam/oidc/login` (когда настроен OIDC)
- `GET /v1/iam/oidc/callback` (зарегистрированный OIDC redirect endpoint)

Маршруты начальной настройки:

- `GET /v1/iam/bootstrap`
- `POST /v1/iam/bootstrap`

API-токены проходят те же проверки авторизации, что и пользователи сессии.

## Единый вход через OIDC

IronRAG поддерживает серверный вход OpenID Connect Authorization Code с PKCE.
Чтобы выключить SSO, оставьте все обязательные OIDC-настройки пустыми. Если
задана хотя бы одна обязательная настройка, запуск требует полный набор и
завершается ошибкой вместо неявного перехода на другой способ входа.

| Переменная | Назначение |
|---|---|
| `IRONRAG_OIDC_ISSUER_URL` | Канонический URL издателя, опубликованный поставщиком удостоверений. |
| `IRONRAG_OIDC_CLIENT_ID` | Идентификатор конфиденциального клиента, зарегистрированного для IronRAG. |
| `IRONRAG_OIDC_CLIENT_SECRET` | Секрет конфиденциального клиента. Передавайте его только через окружение с секретами времени выполнения. |
| `IRONRAG_OIDC_REDIRECT_URL` | Точный зарегистрированный URL обратного вызова. Например, для развёртывания на `https://ironrag.example.com`: `https://ironrag.example.com/v1/iam/oidc/callback`. |
| `IRONRAG_OIDC_REQUIRED_GROUP` | Утверждение о группе, необходимое для допуска пользователя. |
| `IRONRAG_OIDC_BOOTSTRAP_ADMIN_SUBJECT` | Необязательное точное значение OIDC `sub`, которому при первом создании пользователя назначается локальная роль администратора. |

Секрет клиента — учётные данные: храните его в менеджере секретов развёртывания
(например, Vault) и передавайте API через переменную окружения. Не кладите его
в Git, аргументы командной строки или образ. Необязательный начальный субъект —
селектор удостоверения, а не секрет; получите и проверьте его неизменяемый
`sub` у поставщика удостоверений до первого входа пользователя.

Обратный вызов принимает только поставщика, найденного по настроенному
издателю. Перед созданием сессии IronRAG он проверяет издателя, аудиторию,
подпись, срок действия, `nonce`, привязку PKCE к коду авторизации и одноразовое
состояние. Состояние привязано к браузеру и расходуется один раз; неуспешный
или повторный обратный вызов не создаёт сессию.

Допущенный пользователь создаётся при первом входе по паре издателя и `sub`.
Электронная почта — только данные профиля: IronRAG не связывает по ней учётную
запись с паролем или другую учётную запись OIDC. Новый пользователь OIDC
получает локальную роль `viewer`. Необязательный начальный субъект получает
локальную роль администратора только при первом создании именно этого
удостоверения; последующая настройка не повышает существующего пользователя.

Требуемая группа OIDC — проверка допуска, а не разрешение или роль IronRAG.
Выпуск токена и область каждого токена по-прежнему определяют локальная роль и
разрешения IronRAG. Поэтому пользователь OIDC может создавать и использовать
токены только при разрешении локальной авторизации; принадлежность к группе
сама по себе не делает пользователя администратором IronRAG.

### Локальный администратор с паролем

OIDC не отменяет отдельно настроенного администратора с паролем. Его пароль
остаётся в `IRONRAG_UI_BOOTSTRAP_ADMIN_PASSWORD` вместе с обязательными
начальной учётной записью и адресом электронной почты. При запуске IronRAG
сверяет этот пароль только для точно настроенного локального администратора с
паролем. Он не меняет учётные данные пользователя OIDC и не связывает
удостоверение OIDC с этой учётной записью. В управляемом развёртывании
передавайте этот пароль из того же менеджера секретов, что и другие учётные
данные времени выполнения.

## Жизненный цикл токена

1. Создайте токен в интерфейсе администратора или через `ironrag-cli create-token`.
2. Один раз скопируйте открытое значение токена.
3. Сервер хранит только хеш токена.
4. Клиент аутентифицируется через `Authorization: Bearer inrg_...`.
5. Для каждого HTTP- или MCP-вызова разрешения определяются для целевой области.

Токены, созданные из сессии OIDC, выпускаются от имени пользователя IronRAG и
подчиняются тем же правилам хеширования, области действия, отзыва и аудита, что
и токены из сессии с паролем.

## Видимость инструментов MCP

`tools/list` фильтруется по разрешениям.

- Инструменты обнаружения и чтения требуют доступа на чтение к целевой области.
- Инструменты изменения документов и веб-приёма требуют доступа на запись.
- Инструменты состояния требуют `ops_read` или более сильного доступа, уже покрывающего целевую библиотеку.
- Инструменты создания каталога требуют административного доступа.

Если токен не может использовать инструмент, он не появляется в списке.

Если токен ограничен ровно одним рабочим пространством или библиотекой,
инструменты MCP и API поиска автоматически подставляют `workspace_id` и
`library_id` из области токена.

## Правила безопасности

- Токены хешируются до сохранения.
- Пароли хешируются через Argon2id.
- Просроченные разрешения игнорируются.
- Административный доступ области `system` намеренно широк; по возможности
  используйте область рабочего пространства или библиотеки.
