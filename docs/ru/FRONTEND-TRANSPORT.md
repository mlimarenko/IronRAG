# Сетевой доступ к фронтенду

Стандартный Compose открывает интерфейс по **HTTP** на порту `19000`. Это
подходит, когда TLS завершается на ingress или обратном прокси; для SSE
маршрутов ассистента отключите `proxy_buffering`.

Образ фронтенда может отдавать **TLS напрямую**: смонтируйте сертификат и ключ
в `/etc/nginx/tls/tls.crt` и `/etc/nginx/tls/tls.key`, опубликуйте `443/tcp` и
`443/udp`. При наличии файлов nginx включает HTTP/2, объявляет HTTP/3 over QUIC
через `Alt-Svc`, а проксирование API оставляет на HTTP/1.1 — так стабильнее
стриминг ответов и крупные snapshot upload'ы.

## Пример Compose

```yaml
services:
  frontend:
    ports:
      - "443:443/tcp"
      - "443:443/udp"
    volumes:
      - ./certs/fullchain.pem:/etc/nginx/tls/tls.crt:ro
      - ./certs/privkey.pem:/etc/nginx/tls/tls.key:ro
```

## Проверка обратного прокси

Когда TLS завершается перед контейнером фронтенда:

- `proxy_buffering off` и `proxy_request_buffering off` на SSE-маршрутах ассистента.
- Сохраняйте заголовки `Upgrade` / `Connection`, если позже добавите WebSocket.
- Направьте upstream на сервис фронтенда (`IRONRAG_API_UPSTREAM` внутри
  контейнера по-прежнему указывает на бэкенд для `/v1/*`).

## Брендинг развёртывания

Фронтенд читает **`/branding.json` до отрисовки интерфейса**. В образе поставляется
`{}`: для пропущенных настроек остаются название IronRAG и встроенный знак. Это
runtime-конфигурация, а не build-переменные `VITE_*`: один образ можно использовать
с разным брендингом без пересборки.

```json
{
  "displayName": "База знаний команды",
  "logoUrl": "/brand/logo.svg",
  "iconUrl": "/brand/icon.svg",
  "faviconUrl": "/brand/favicon.png"
}
```

`displayName` — обычный текст длиной 1–120 символов после удаления крайних
пробелов. `logoUrl` задаёт основной знак, `iconUrl` — компактный знак,
`faviconUrl` — иконку браузера. Если иконка не указана, используется логотип;
если favicon не указан, используется иконка. Название также задаёт заголовок
вкладки и Open Graph title. HTML и пользовательский CSS не поддерживаются.
Неизвестные поля, включая настройки прав, отклоняются: брендинг **не меняет**
роли, контроль доступа и права на разделы навигации.

Изображения задаются путями от корня сайта или абсолютными HTTP(S) URL с
**тем же origin**, включая протокол и порт. Внешние и protocol-relative URL,
встроенные credentials, `javascript:`, `data:`, `blob:` и некорректные URL
отклоняются. Отдавайте изображения через фронтенд; его CSP остаётся прежним.

Создайте `branding.json` и каталог `brand/` рядом с Compose-файлом. Добавьте
read-only mounts в `compose.override.yaml`:

```yaml
services:
  frontend:
    volumes:
      - ./branding.json:/usr/share/nginx/html/branding.json:ro
      - ./brand:/usr/share/nginx/html/brand:ro
```

Выполните `docker compose up -d frontend` и обновите страницу. Эти mounts нужны
только фронтенду. Существующая Docker-сборка копирует JSON вместе с остальными
public assets; переменные окружения образа и изменения бэкенда не нужны.
В Kubernetes смонтируйте файл ConfigMap по тому же пути и отдавайте изображения
с того же origin. Конфигурация запрашивается с `no-store`; публикуйте её вместе
с изображениями и меняйте имена файлов при обновлении изображений. Таймаут запроса
конфигурации — пять секунд. Недоступный
или некорректный JSON блокирует startup: показываются существующий локализованный
экран ошибки и сообщение в консоли с путём `/branding.json`, а не скрытое
игнорирование настроек. Исправьте файл и обновите страницу.

Для локального Vite измените `apps/web/public/branding.json`, изображения
положите в `apps/web/public/brand/`; не коммитьте настройки конкретного деплоя.
Компоненты используют `getBranding().displayName` из `@/app/branding` и `Brand` /
`BrandMark` из `@/app/Brand`. `BrandMark` принимает `compact`, `size` и `className`;
это декоративное изображение, поэтому при использовании без текста добавьте
доступное название в вызывающем компоненте.
